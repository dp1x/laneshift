# First Kev-0.8B LoRA fine-tune

## Context length: `--max_state` is not the serving context

`--max_state 384` is Kev's minimum *training state-token cap*, not a 384-token
model context. Kev's `MAX_STATE`/`MAX_TRAIN_STATE` constants govern how many
state tokens the encoder admits; the Qwen backbone itself has a much larger
window. The LANESHIFT production graph is L256, and every `kev-v2-scene` row is
rendered to at most 256 total tokens by the dataset builder.

Train with `--max_state 384` so the encoder never truncates a long state. Then
export and evaluate the original and fine-tuned checkpoints at the **same**
L256 graph length. A 384-token fine-tuned graph compared with the original L256
graph is not a valid comparison. The dataset manifest records the maximum
rendered prompt (255) and the L256 gate.

This directory contains the first LANESHIFT Kev fine-tuning path:

- `kev_finetune.ipynb` downloads the pinned upstream Kev training code, validates
  the seed-disjoint pilot dataset, runs the LoRA delta fine-tune from
  `jaredpalmer/kev-0.8b@v1.0`, and scores the original and fine-tuned
  checkpoints on the same held-out rows.
- `kev_pilot_data/` is the derived Kev-format dataset, generated by
  `python/export_kev_pilot.py` from the preserved 1,348-row pilot export.

The notebook has not been executed on this host. It requires a Colab CUDA
runtime with Python 3.12 or 3.13; the local Windows ARM64 host has Python 3.14
and no PyTorch ARM64 wheel.

## Training command

The notebook runs this command with `python -m kev.train`:

```text
--data /content/data/kev_train.jsonl
--base Qwen/Qwen3.5-0.8B-Base
--base_revision dc7cdfe2ee4154fa7e30f5b51ca41bfa40174e68
--init_from jaredpalmer/kev-0.8b@v1.0
--lora 16 --head_dim 256 --lora_targets all
--lr 2e-5 --epochs 1 --batch 1 --accum 8
--dtype bf16 --weights_dtype bf16 --checkpointing 1
--max_state 384
--p_none 0 --p_none_distract 0 --p_distract 0 --p_none_pair 0
--device cuda --seed 1 --out /content/runs/laneshift-kev-lora
```

Use `fp32` for both dtype flags on a T4; the notebook detects bf16 support.
`--max_state 384` is Kev's minimum training state budget. The compact prompts
are much shorter, and the production ONNX graph is L256.

## Evaluation

The notebook scores validation and test with the original checkpoint and the
fine-tuned checkpoint. Both models see the same records, option sets, and
option order, and both are scored at temperature 1.0 (raw logits) so the
calibration metrics use the same scale. It writes `eval_metrics.json`, per-row predictions, a checkpoint
manifest with adapter/head hashes, and a gameplay evaluation plan for the
held-out seeds 7, 29, and 61.

The test split is never used for training. The NumPy MLP row in the notebook is
a reference from the pilot report; it uses a different input representation and
is not a controlled Kev comparison.

## Claim boundary

The labels are deterministic rule-based teacher actions, and the prompt is the
compact `c1` projection. This is an imitation experiment. It can show whether
LoRA moves Kev toward the teacher on held-out seeds. Gameplay improvement
requires the fine-tuned checkpoint to be merged/exported or served, then run
through the matched `experiment_runner.py` comparison on the same gameplay
seeds.
